# 3.4 The Core Objects Glossary

## Concept Recap

Before touching kubectl in Module 4, get comfortable with the vocabulary you'll be using constantly.

## Objective

Learn the plain-English definition of every object you'll create in Module 4, before you create any of them.

## Prerequisites

- Labs 3.1-3.3 complete

## Steps

### Step 1: The glossary

- **Pod** - the smallest deployable unit; usually one container, wrapped with a stable network identity.
- **Deployment** - manages a set of identical Pods (a 'ReplicaSet' under the hood), handling scaling and rolling updates. You'll create Deployments far more often than raw Pods.
- **Service** - a stable network address that routes to a changing set of Pods (since Pods can be replaced/rescheduled, their IPs change - a Service gives you something stable to point at).
- **Namespace** - a way to logically divide a cluster (e.g. one namespace per team or environment) so resources don't collide and access can be scoped.
- **ConfigMap** - non-sensitive configuration data injected into Pods (like a `.env` file, but managed by Kubernetes).
- **Secret** - like a ConfigMap, but intended for sensitive values (passwords, tokens) - base64-encoded, not encrypted by default.
- **Label / Selector** - key-value tags on objects (labels), and queries that match them (selectors) - this is literally how a Service finds which Pods to route to.

### Step 2: Map each to something you already know from Docker/Compose

- Pod ≈ a single `docker run` container (roughly)
- Deployment ≈ Compose's `--scale` plus automatic restart-on-failure (Lab 1.8/2.8), but continuous and cluster-wide
- Service ≈ Compose's automatic DNS-by-service-name (Lab 2.4), but for a Kubernetes cluster
- Namespace ≈ roughly like having several separate Compose projects, but within ONE cluster
- ConfigMap/Secret ≈ Compose's `.env` file (Lab 2.6), split into non-sensitive vs. sensitive

## Check Your Understanding

**Q1: Why do you create Deployments instead of raw Pods almost all the time?**

<details><summary>Answer</summary>

Deployments add automatic scaling, self-healing, and rolling updates on top of Pods - a raw Pod on its own won't be replaced if it dies.

</details>

**Q2: Why does a Service exist at all instead of just using a Pod's IP address directly?**

<details><summary>Answer</summary>

Pod IPs change whenever a Pod is replaced (crash, update, rescheduling) - a Service gives you one stable address regardless of which specific Pods are currently backing it.

</details>

**Q3: What's the main practical difference between a ConfigMap and a Secret?**

<details><summary>Answer</summary>

Secrets are meant for sensitive data and are base64-encoded (not truly encrypted by default - real encryption at rest requires additional cluster configuration); ConfigMaps are for plain, non-sensitive settings.

</details>

## Common Mistakes

- **Assuming a Secret is automatically encrypted and fully secure by default** - Base64 is just an ENCODING, not encryption - anyone with API access to read the Secret can trivially decode it. Real secret protection needs additional cluster-level encryption-at-rest configuration.
- **Trying to point traffic directly at a Pod's IP in production-style setups** - Always go through a Service - Pod IPs are not stable.

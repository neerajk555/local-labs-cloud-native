# 3.2 Pods, Nodes, and the Control Plane

## Concept Recap

A **node** is one machine (real or virtual) in the cluster. A **Pod** is the smallest deployable unit in Kubernetes - usually one container, sometimes a few tightly-coupled ones sharing network/storage. The **control plane** is the cluster's brain: it decides which node each Pod runs on, watches for failures, and works continuously to keep reality matching what you declared.

## Steps

### Step 1: Read: Nodes

Think of nodes as the 'worker machines' - this is where your actual containers run. A cluster typically has multiple nodes for redundancy and capacity.

### Step 2: Read: Pods

A Pod wraps one or more containers that need to be scheduled together, share the same network address, and can share storage volumes. Most Pods have exactly one container - the multi-container case (like Lab 5.1's sidecar pattern from the AWS labs) is the exception, not the rule.

### Step 3: Read: The control plane

The control plane includes the API server (the front door for all commands, including kubectl), the scheduler (decides which node a new Pod goes on), and the controller manager (continuously reconciles actual state with your desired state - e.g. restarting a Pod that died).

## Check Your Understanding

**Q1: What's the smallest deployable unit in Kubernetes?**

<details><summary>Answer</summary>

A Pod, not a container directly - even a single-container app runs inside a one-container Pod.

</details>

**Q2: What decides which node a new Pod runs on?**

<details><summary>Answer</summary>

The scheduler, part of the control plane.

</details>

**Q3: If a node crashes, does Kubernetes automatically move its Pods to another node?**

<details><summary>Answer</summary>

Yes, for Pods managed by controllers like Deployments (Module 4) - the control plane detects the failure and reschedules replacements elsewhere.

</details>

## Common Mistakes

- **Saying 'container' when you mean 'Pod'** - Kubernetes schedules and manages Pods, not individual containers directly - this distinction matters once you get to networking and storage.
- **Thinking the control plane runs your application code** - It doesn't - it only manages/schedules; your actual app containers run on worker nodes.

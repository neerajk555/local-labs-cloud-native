# 3.3 Declarative vs. Imperative (Why YAML, Why 'Desired State')

## Concept Recap

An IMPERATIVE approach says 'do this specific action now' (like `docker run`). A DECLARATIVE approach says 'this is what I want to exist' and lets the system figure out how to get there - and KEEP it there, continuously. Kubernetes is built around the declarative model.

## Objective

Understand why Kubernetes YAML describes desired state instead of listing commands to run.

## Prerequisites

- Lab 3.2 complete

## Steps

### Step 1: Read: The imperative example

`docker run -d nginx` is imperative: 'start a container right now.' If that container crashes, nothing automatically restarts it unless you also configured `--restart` (Lab 1.8) - Docker doesn't continuously ENFORCE that a container should exist.

### Step 2: Read: The declarative example

A Kubernetes Deployment YAML says: 'there should ALWAYS be 3 replicas of this Pod running.' This isn't a one-time command - Kubernetes continuously watches and reconciles. If a Pod dies, a node fails, or you manually delete one, Kubernetes immediately starts a replacement to get back to 3, without you doing anything.

### Step 3: Read: Why this matters for updates too

When you change a Deployment's YAML (e.g. a new image version), Kubernetes doesn't just imperatively run 'stop old, start new.' It reconciles gradually - the same rolling-update mechanism you'll use hands-on in Lab 4.8.

## Check Your Understanding

**Q1: Is `docker run` imperative or declarative?**

<details><summary>Answer</summary>

Imperative - it's a one-time instruction to perform an action now.

</details>

**Q2: If you manually delete a Pod that's managed by a Deployment, what happens?**

<details><summary>Answer</summary>

Kubernetes notices the actual state (2 Pods) doesn't match the desired state (3 Pods) and immediately creates a replacement.

</details>

**Q3: Why does this model make rolling updates safer?**

<details><summary>Answer</summary>

Kubernetes can reconcile toward the new desired state gradually and can compare actual vs. desired at every step, rather than blindly executing a fixed sequence of commands.

</details>

## Common Mistakes

- **Thinking you need to manually restart failed Pods in a Deployment** - You don't - this is exactly what the declarative model + control plane automates.
- **Editing a live Pod directly instead of the Deployment that manages it** - Direct Pod edits get overwritten/discarded the next time the controller reconciles - always edit the higher-level object (Deployment) instead.

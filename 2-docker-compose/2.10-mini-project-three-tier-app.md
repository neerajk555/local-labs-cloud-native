# 2.10 Mini-Project: Build a Full 3-Tier App From a Spec

## Concept Recap

This project combines every Compose concept from this module: build vs image, depends_on, networking by name, volumes, .env files, scaling, and profiles.

## Objective

Build a complete 3-tier app from a written spec, with minimal hand-holding.

## Prerequisites

- Labs 2.1-2.9 complete

## Steps

### Step 1: The spec

Build a compose.yaml satisfying ALL of these requirements:

1. A `db` service using postgres:16, with its password sourced from a `.env` file (not hardcoded), and its data in a named volume that survives `docker compose down` (without -v)
2. An `api` service built from a local Dockerfile (write a tiny Node.js app yourself, like in Lab 2.7), that reads the db's hostname from an environment variable and depends on `db`
3. A `web` service using nginx, exposed on a host port defined in your `.env` file (not hardcoded in compose.yaml), that depends on `api`
4. An optional `adminer` service gated behind a `debug` profile, for inspecting the database
5. The `api` service should be scalable to 3 replicas without any compose.yaml changes

### Step 2: Verification checklist

- `docker compose up -d` starts db, api, and web, but NOT adminer
- `docker compose --profile debug up -d` also starts adminer
- `docker compose up -d --scale api=3` runs 3 api replicas
- Changing WEB_PORT in .env and restarting changes which host port nginx listens on
- `docker compose down` (no -v) followed by `docker compose up -d` keeps your db-data volume intact

## Common Mistakes

- **Hardcoding the db password directly in compose.yaml instead of using .env** - Requirement 1 specifically asks for this to be externalized - revisit Lab 2.6 if you skipped it.
- **Not testing the scale requirement** - It's easy to write compose.yaml in a way that ACCIDENTALLY blocks scaling (e.g. by setting container_name on api) - always actually test with --scale.

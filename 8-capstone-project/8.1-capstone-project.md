# 8.1 Capstone: Multi-Service App on kind with Ingress, ConfigMaps, and Helm

## Concept Recap

This is a portfolio-style final project combining every module: Docker fundamentals, Compose, Kubernetes core objects, workloads, Helm, and Ingress. Minimal hand-holding is intentional - use this as a genuine test of what you've retained, and refer back to earlier labs whenever you get stuck rather than skipping ahead.

## Objective

Build, containerize, and deploy a small multi-service app to a local kind cluster, packaged as a Helm chart and exposed through Ingress.

## Prerequisites

- All of Modules 0-7 complete

## Steps

### Step 1: The spec

Build an app with these THREE services:

1. **`api`** - a small HTTP service (Node.js, Python, or anything you like) that returns some JSON, reads at least one setting from a ConfigMap-injected environment variable, and has a working readiness probe
2. **`worker`** - a Job (not a long-running service) that runs once, does something trivial (e.g. prints a message referencing a value from the same ConfigMap), and completes successfully
3. **`web`** - nginx (or similar) serving a static page, that also proxies `/api` requests to the `api` service internally

All of this must be packaged as a **single Helm chart** with:
- A `values.yaml` exposing at least: image tags for api/web, the ConfigMap's values, and replica count for `api`
- Templated Deployment/Service manifests for `api` and `web`
- A templated Job manifest for `worker`
- A templated ConfigMap
- An Ingress resource exposing `web` at a hostname of your choice, using what you learned in Module 7 (including correct kind cluster setup for Ingress)

### Step 2: Build order suggestion (not mandatory)

1. Build and test each app piece with plain `docker run` first (Module 1 skills)
2. Get all three working together locally with Compose before touching Kubernetes at all (Module 2 skills) - this isolates app bugs from Kubernetes/Helm bugs
3. Write raw Kubernetes YAML for everything and get it working with plain `kubectl apply` (Module 4-5 skills)
4. ONLY THEN convert the working raw YAML into a templated Helm chart (Module 6 skills)
5. Add Ingress last (Module 7 skills)

### Step 3: Self-grading rubric

- [ ] `helm install capstone ./mychart` succeeds with no errors
- [ ] `kubectl get pods` shows api and web Running, and worker's Job shows Completed
- [ ] Visiting your Ingress hostname in a browser (or via curl with a Host header) shows the static page
- [ ] Requesting `/api` through that same hostname returns the api service's JSON response (proving the proxy works)
- [ ] `kubectl logs job/worker-<...>` shows it correctly read the ConfigMap value
- [ ] `helm upgrade capstone ./mychart --set api.replicaCount=3` scales api without touching web or worker
- [ ] `helm rollback capstone 1` correctly reverts that scaling change
- [ ] Deliberately breaking api's readiness probe removes it from web's traffic without a full restart (Lab 4.10's lesson), and you can prove this with `kubectl get endpoints`

## Common Mistakes

- **Jumping straight to Helm without getting raw YAML working first** - Debugging templating issues AND app issues at the same time is much harder - always get plain kubectl apply working first, exactly as the build order suggests.
- **Skipping the rubric's 'deliberately break something' checks** - These are the checks that actually prove understanding, not just that you copy-pasted correctly - don't skip them even though they take extra time.

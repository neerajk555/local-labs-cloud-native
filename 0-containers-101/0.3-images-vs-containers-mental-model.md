# 0.3 Images vs. Containers: The Mental Model

## Concept Recap

Every container you create from the same image starts identical, but they are completely independent once running - changes inside one container never affect another, or the original image. This is because containers use a layered, copy-on-write filesystem on top of the image's read-only layers.

## Objective

See with your own eyes that one image can produce many independent containers.

## Steps

### Step 1: Create two containers from the same image

```bash
docker run -d --name c1 ubuntu sleep 300
docker run -d --name c2 ubuntu sleep 300
```

### Step 2: Change a file inside only c1

```bash
docker exec c1 sh -c 'echo hello > /tmp/note.txt'
```

### Step 3: Confirm c2 doesn't have it

```bash
docker exec c2 ls /tmp/
```

You should NOT see note.txt here.

### Step 4: Confirm the image itself is untouched

```bash
docker run --rm ubuntu ls /tmp/
```

A brand-new container from the same image also won't have note.txt.

## Check Your Understanding

**Q1: If I write a file inside a running container, does it change the image?**

<details><summary>Answer</summary>

No - the image stays read-only. The change lives in the container's own writable layer.

</details>

**Q2: Do two containers from the same image share filesystem changes?**

<details><summary>Answer</summary>

No - each container gets its own independent writable layer.

</details>

**Q3: What happens to that writable layer if you `docker rm` the container?**

<details><summary>Answer</summary>

It's deleted along with the container, unless the data was in a mounted volume.

</details>

## Common Mistakes

- **Assuming containers from the same image share state** - They don't, by default - each is fully isolated.
- **Forgetting that container filesystem changes are lost on removal** - This is exactly why volumes exist - covered in Lab 1.4.

## Cleanup

```bash
docker rm -f c1 c2
```

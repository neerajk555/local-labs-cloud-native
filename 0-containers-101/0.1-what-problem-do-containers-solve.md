# 0.1 What Problem Do Containers Solve?

## Concept Recap

Before containers, teams shipped code that worked "on my machine" but broke on the server, because the server had different library versions, a different OS, or missing dependencies. Virtual machines (VMs) fixed this by packaging a whole operating system with the app - but VMs are heavy: each one boots its own kernel, uses gigabytes of disk, and takes minutes to start. A **container** packages just the app and its dependencies, and shares the host machine's kernel instead of bringing its own. That makes containers start in under a second and use megabytes instead of gigabytes, while still giving the app an isolated, consistent environment.

## Steps

### Step 1: Read: Container vs Virtual Machine

A VM virtualizes hardware: each VM has its own full OS kernel, drivers, and boot process. A container virtualizes the OS: many containers share one host kernel, but each sees its own isolated filesystem, process list, and network stack. Think of a VM as a separate house with its own foundation, plumbing, and utilities. A container is more like an apartment - separate space, shared building infrastructure.

### Step 2: Read: Why this matters in practice

Because containers are lightweight, you can run dozens of them on a laptop that could only run two or three VMs. Because they package dependencies with the app, "works on my machine" becomes "works everywhere," since the container carries its own copy of whatever runtime/libraries it needs.

## Check Your Understanding

**Q1: Does a container include its own operating system kernel?**

<details><summary>Answer</summary>

No - it shares the host machine's kernel. Only the app and its dependencies are packaged.

</details>

**Q2: Why do containers start faster than VMs?**

<details><summary>Answer</summary>

They don't need to boot a full OS/kernel - they just start a process using the already-running host kernel.

</details>

**Q3: What problem does packaging dependencies with the app solve?**

<details><summary>Answer</summary>

"Works on my machine" bugs caused by version mismatches between environments.

</details>

## Common Mistakes

- **Thinking a container is a tiny VM** - It's a fundamentally different isolation mechanism - no separate kernel, no separate boot process.
- **Assuming containers are always more secure than VMs** - Because containers share a kernel, isolation is weaker than a VM's - this matters for security-sensitive workloads.

# 5.1 Jobs: Run-to-Completion Tasks

## Concept Recap

A Deployment expects its Pods to run FOREVER (restarting if they exit). A Job expects its Pod to run ONCE and finish successfully - for batch tasks, migrations, or one-off scripts.

## Objective

Run a Job and understand how its success/failure semantics differ from a Deployment's.

## Prerequisites

- Module 4 complete

## Steps

### Step 1: Create a Job

```bash
kubectl create job hello-job --image=busybox -- echo 'batch task complete'
```

### Step 2: Watch it run to completion

```bash
kubectl get jobs -w
```

Ctrl+C once COMPLETIONS shows 1/1.

### Step 3: See its output

```bash
kubectl logs job/hello-job
```

### Step 4: Confirm the Pod is NOT restarted after finishing

```bash
kubectl get pods
```

Status shows Completed, not Running - and it stays that way, unlike a Deployment's Pods.


## Try It Yourself

**Exercise 1:** Create a Job that deliberately fails (`exit 1`) and observe how many times Kubernetes retries it by default before giving up.

<details><summary>Hint (try first without peeking)</summary>

`kubectl create job fail-job --image=busybox -- sh -c 'exit 1'`, then `kubectl get pods` repeatedly - default `backoffLimit` is 6 retries.

</details>

## Check Your Understanding

**Q1: What's the fundamental difference in expectation between a Deployment's Pod and a Job's Pod?**

<details><summary>Answer</summary>

A Deployment expects its Pod to run indefinitely and restarts it if it exits; a Job expects its Pod to run ONCE and complete successfully, and does not restart a successfully-completed Pod.

</details>

**Q2: What happens by default if a Job's Pod fails?**

<details><summary>Answer</summary>

Kubernetes retries it, up to a default backoffLimit of 6 attempts, before marking the Job as failed.

</details>

## Common Mistakes

- **Using a Deployment for a one-off migration script** - The Deployment would keep restarting the script forever since it expects continuous running - use a Job instead.
- **Forgetting completed Job Pods stick around (in Completed state)** - They're not automatically cleaned up unless you set `ttlSecondsAfterFinished` - clean up manually with `kubectl delete job` when done.

## Cleanup

```bash
kubectl delete job hello-job fail-job 2>/dev/null || true
```

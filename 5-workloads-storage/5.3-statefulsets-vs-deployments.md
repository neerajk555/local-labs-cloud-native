# 5.3 StatefulSets vs. Deployments: When Order/Identity Matters

## Concept Recap

A Deployment's Pods are interchangeable - any replica can be replaced by an identical one. A StatefulSet's Pods have STABLE, PREDICTABLE names and start up in ORDER - needed for apps like databases where identity and startup sequence matter.

## Objective

Deploy a StatefulSet and observe its predictable naming, contrasted with a Deployment's random naming.

## Prerequisites

- Lab 4.4 complete

## Steps

### Step 1: Compare Deployment Pod names (random suffix)

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=3
kubectl get pods -l app=web
```

Names look like web-7d9f8c9b76-x7k2p - unpredictable.

### Step 2: Create a headless Service (required for StatefulSets)

```bash
cat > headless.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: stateful-svc
spec:
  clusterIP: None
  selector:
    app: stateful-demo
  ports:
    - port: 80
EOF
kubectl apply -f headless.yaml
```

### Step 3: Create a StatefulSet

```bash
cat > statefulset.yaml <<'EOF'
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: stateful-demo
spec:
  serviceName: stateful-svc
  replicas: 3
  selector:
    matchLabels:
      app: stateful-demo
  template:
    metadata:
      labels:
        app: stateful-demo
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
EOF
kubectl apply -f statefulset.yaml
```

### Step 4: See the predictable, ordered naming

```bash
kubectl get pods -l app=stateful-demo -w
```

Names are stateful-demo-0, stateful-demo-1, stateful-demo-2 - and they start up IN THAT ORDER, one at a time, unlike the Deployment's parallel/random creation.

## Check Your Understanding

**Q1: What's the key naming difference between Deployment Pods and StatefulSet Pods?**

<details><summary>Answer</summary>

Deployment Pods get random suffixes and are interchangeable; StatefulSet Pods get predictable, ordered names (like -0, -1, -2) that persist across replacement.

</details>

**Q2: Why do StatefulSets require a headless Service?**

<details><summary>Answer</summary>

It provides stable DNS entries for each individual Pod (like stateful-demo-0.stateful-svc), which ordinary Pods/Deployments don't need since they're interchangeable.

</details>

**Q3: Give a real example of an app that needs StatefulSet-style guarantees.**

<details><summary>Answer</summary>

A database cluster (like Postgres or Cassandra) where each replica has a distinct role/identity and needs stable network identity and ordered startup (e.g. primary must start before replicas).

</details>

## Common Mistakes

- **Using a StatefulSet for a stateless web app** - Unnecessary complexity - use a Deployment unless you specifically need stable identity or ordered startup/shutdown.
- **Forgetting the headless Service requirement** - A StatefulSet without a matching headless Service (clusterIP: None) won't get the per-Pod DNS entries that are the whole point of using one.

## Cleanup

```bash
kubectl delete -f statefulset.yaml -f headless.yaml
kubectl delete deployment web
rm -f headless.yaml statefulset.yaml
```

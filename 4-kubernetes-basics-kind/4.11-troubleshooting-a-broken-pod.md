# 4.11 Troubleshooting a Broken Pod (Guided Debugging Exercise)

## Concept Recap

This lab deliberately creates several common real-world failures and walks you through diagnosing each with the tools from Lab 4.3.

## Objective

Diagnose and fix three intentionally broken Pod configurations.

## Prerequisites

- Labs 4.1-4.10 complete

## Steps

### Step 1: Failure 1: Image typo

```bash
kubectl run broken1 --image=ngnix:1.27
```

Note the typo: 'ngnix' not 'nginx'.

### Step 2: Diagnose failure 1

```bash
kubectl get pods
kubectl describe pod broken1
```

Look for ImagePullBackOff / ErrImagePull in the status and Events - this means Kubernetes can't find the image.

### Step 3: Failure 2: Resource request too high for the cluster

```bash
cat > broken2.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: broken2
spec:
  containers:
    - name: hog
      image: nginx:1.27
      resources:
        requests:
          memory: "500Gi"
EOF
kubectl apply -f broken2.yaml
```

### Step 4: Diagnose failure 2

```bash
kubectl get pods
kubectl describe pod broken2
```

Look for 'Pending' status and an event like 'Insufficient memory' - the scheduler can't find a node with enough capacity.

### Step 5: Failure 3: Crashing application

```bash
kubectl run broken3 --image=alpine -- sh -c 'exit 1'
```

### Step 6: Diagnose failure 3

```bash
kubectl get pods
kubectl logs broken3
kubectl describe pod broken3
```

Look for CrashLoopBackOff - the container starts, immediately exits, and Kubernetes keeps retrying with increasing delay.


## Try It Yourself

**Exercise 1:** Fix all three: correct the image name for broken1, lower the memory request to something reasonable for broken2, and change broken3's command to something that doesn't exit immediately.

## Check Your Understanding

**Q1: What status indicates Kubernetes can't find or download the specified image?**

<details><summary>Answer</summary>

ImagePullBackOff or ErrImagePull.

</details>

**Q2: What status indicates a Pod can't be scheduled onto any node?**

<details><summary>Answer</summary>

Pending, usually with an Events message explaining why (like insufficient resources).

</details>

**Q3: What status indicates a container keeps starting and immediately exiting?**

<details><summary>Answer</summary>

CrashLoopBackOff.

</details>

**Q4: For which of these three would `kubectl logs` be most useful, and why?**

<details><summary>Answer</summary>

CrashLoopBackOff - since the container actually starts and runs briefly, its logs often show the real error (unlike ImagePullBackOff or Pending, where the container never starts at all).

</details>

## Common Mistakes

- **Jumping straight to logs for a Pending or ImagePullBackOff Pod** - Those failures happen BEFORE the container ever starts, so there ARE no logs yet - use `describe` and check Events instead.
- **Not reading the Events timestamps in describe output** - Events are shown oldest-to-newest - the MOST RECENT events at the bottom are usually most relevant to the current problem.

## Cleanup

```bash
kubectl delete pod broken1 broken3 2>/dev/null || true
kubectl delete -f broken2.yaml 2>/dev/null || true
rm -f broken2.yaml
```

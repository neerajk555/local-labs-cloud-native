# 4.9 ConfigMaps and Secrets

## Concept Recap

ConfigMaps and Secrets (Lab 3.4's glossary) inject configuration into Pods without baking it into the image - the Kubernetes equivalent of Lab 1.5's environment variables and Lab 2.6's .env files.

## Objective

Inject both a ConfigMap and a Secret into a running Deployment as environment variables.

## Prerequisites

- Lab 4.4 complete
- Lab 1.5 complete

## Steps

### Step 1: Create a ConfigMap

```bash
kubectl create configmap app-config --from-literal=GREETING=hello
```

### Step 2: Create a Secret

```bash
kubectl create secret generic app-secret --from-literal=API_KEY=demo123
```

### Step 3: Create a Deployment and inject both

```bash
kubectl create deployment web --image=nginx:1.27
kubectl set env deployment/web --from=configmap/app-config
kubectl set env deployment/web --from=secret/app-secret
```

### Step 4: Verify both are set inside a Pod

```bash
kubectl get pods
kubectl exec <paste-pod-name> -- env | grep -E 'GREETING|API_KEY'
```

### Step 5: See what a Secret actually looks like stored (base64, not encrypted)

```bash
kubectl get secret app-secret -o jsonpath='{.data.API_KEY}' | base64 -d
```

This proves Lab 3.4's point: base64 is trivially reversible, not real encryption.

## Check Your Understanding

**Q1: What's the main practical difference in how you'd store an API key vs. a feature-flag setting?**

<details><summary>Answer</summary>

The API key belongs in a Secret; the feature flag belongs in a ConfigMap - the distinction is about sensitivity, not technical capability (both work almost identically).

</details>

**Q2: Do environment variables update live in a running Pod if you change the underlying ConfigMap?**

<details><summary>Answer</summary>

No - environment variables are set at container start time; you need to restart the Pod (e.g. `kubectl rollout restart deployment/...`) to pick up changes.

</details>

**Q3: Is a Kubernetes Secret truly encrypted by default?**

<details><summary>Answer</summary>

No - it's base64-ENCODED, which is trivially reversible, not encrypted. Real protection requires enabling encryption-at-rest at the cluster level, a separate configuration step.

</details>

## Common Mistakes

- **Treating Secrets as automatically secure without enabling encryption-at-rest** - Anyone with API read access to a Secret can decode it in one command, as you just did - Secrets need RBAC restrictions AND ideally encryption-at-rest to actually be secure.
- **Expecting live config updates without a restart** - Mount ConfigMaps as VOLUMES instead of env vars if you need live-reload behavior - that's a more advanced pattern beyond this lab.

## Cleanup

```bash
kubectl delete deployment web
kubectl delete configmap app-config
kubectl delete secret app-secret
```

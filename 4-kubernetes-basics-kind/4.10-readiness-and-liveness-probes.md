# 4.10 Readiness and Liveness Probes

## Concept Recap

A **liveness probe** answers 'is this container still alive, or should it be restarted?' A **readiness probe** answers 'is this container ready to receive traffic right now?' These are Kubernetes' more precise version of Lab 1.8's Docker health checks, and Services (Lab 4.5) use readiness to decide whether to send traffic to a Pod at all.

## Objective

Configure both probe types and observe the difference between a Pod being restarted vs. temporarily removed from Service traffic.

## Prerequisites

- Lab 4.5 complete
- Lab 1.8 complete

## Steps

### Step 1: Deploy with both probes configured

```bash
cat > probes.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 2
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
EOF
kubectl apply -f probes.yaml
```

### Step 2: Expose it and confirm it's ready

```bash
kubectl expose deployment web --port=80
kubectl get pods
```

READY column shows 1/1 once the readiness probe passes.

### Step 3: Simulate the app becoming unresponsive (not crashed, just unhealthy)

In a real scenario you'd break the health endpoint itself. Here, observe the READY column and understand: if the readiness probe started failing (app still running but broken), the Pod would be marked NotReady and REMOVED from the Service's endpoints - WITHOUT being restarted. Only a failing LIVENESS probe triggers a restart.

## Check Your Understanding

**Q1: What's the key difference between what a failing readiness probe does vs. a failing liveness probe?**

<details><summary>Answer</summary>

A failing readiness probe removes the Pod from Service traffic WITHOUT restarting it; a failing liveness probe causes Kubernetes to RESTART the container.

</details>

**Q2: Why would you want a Pod removed from traffic without being restarted?**

<details><summary>Answer</summary>

Some failures are temporary (e.g. the app is warming up a cache, or briefly overloaded) - restarting wouldn't help and could make things worse; simply pausing traffic until it recovers is the right response.

</details>

**Q3: Which probe determines whether a Service sends traffic to a Pod?**

<details><summary>Answer</summary>

The readiness probe.

</details>

## Common Mistakes

- **Only configuring a liveness probe and assuming it covers both cases** - A liveness-only setup means a temporarily-overloaded-but-not-crashed Pod keeps receiving traffic it can't handle, or gets needlessly restarted - configure both for real apps.
- **Setting initialDelaySeconds too low for a slow-starting app** - This causes the liveness probe to kill the container before it's even finished starting up - tune the delay to match real startup time.

## Cleanup

```bash
kubectl delete -f probes.yaml
kubectl delete service web
rm -f probes.yaml
```

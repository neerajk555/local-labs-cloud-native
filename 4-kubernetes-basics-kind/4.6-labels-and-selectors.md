# 4.6 Labels and Selectors (How Kubernetes Actually Finds Things)

## Concept Recap

Labels are key-value tags you attach to objects. Selectors are queries that match objects by their labels. This is the literal mechanism Services (Lab 4.5) and many other Kubernetes features use to find the right Pods.

## Objective

See exactly how a Service's selector determines which Pods it routes to, by breaking and fixing the connection yourself.

## Prerequisites

- Lab 4.5 complete

## Steps

### Step 1: Create a Deployment with an explicit label

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=2
kubectl get pods --show-labels
```

Notice the auto-assigned label like `app=web`.

### Step 2: Create a Service with a selector that DOESN'T match

```bash
cat > bad-service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: broken-web
spec:
  selector:
    app: wrong-label
  ports:
    - port: 80
EOF
kubectl apply -f bad-service.yaml
```

### Step 3: See the broken result

```bash
kubectl get endpoints broken-web
```

Empty endpoints - the Service exists but has NOTHING to route to, because its selector matches no Pods.

### Step 4: Fix the selector to match

```bash
kubectl delete -f bad-service.yaml
kubectl expose deployment web --port=80 --name=fixed-web
kubectl get endpoints fixed-web
```

Now it has real Pod IPs listed.

## Check Your Understanding

**Q1: What does an empty `kubectl get endpoints <service>` result usually mean?**

<details><summary>Answer</summary>

The Service's selector doesn't match any existing Pods' labels - a very common real-world misconfiguration.

</details>

**Q2: Do Services find Pods by name, or by something else?**

<details><summary>Answer</summary>

By label selector - never by Pod name, since Pod names are unpredictable (randomly suffixed) and Pods get replaced constantly.

</details>

**Q3: If two different Deployments' Pods happen to share the same label, what would happen to a Service selecting on that label?**

<details><summary>Answer</summary>

It would route to Pods from BOTH deployments - selectors don't care which Deployment created a Pod, only whether the labels match.

</details>

## Common Mistakes

- **Assuming a Service is broken due to networking when it's actually a label mismatch** - Always check `kubectl get endpoints <service>` first - an empty list points straight at a selector problem, not a networking problem.
- **Using overly generic labels that accidentally match unrelated Pods** - Be specific with label keys/values (e.g. `app: checkout-api` not just `app: api`) to avoid unintended overlap.

## Cleanup

```bash
kubectl delete deployment web
kubectl delete service fixed-web broken-web 2>/dev/null || true
rm -f bad-service.yaml
```

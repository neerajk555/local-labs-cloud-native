# 4.8 Rolling Updates and Rollbacks

## Concept Recap

A rolling update replaces old Pods with new ones gradually, keeping the app available throughout - this is the declarative reconciliation from Lab 3.3 in action for updates specifically.

## Objective

Perform a zero-downtime update and then roll it back.

## Prerequisites

- Lab 4.4 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Deploy version 1

```bash
kubectl create deployment web --image=nginx:1.26 --replicas=4
```

### Step 2: Update to version 2 and watch the rollout

```bash
kubectl set image deployment/web nginx=nginx:1.27
kubectl rollout status deployment/web
```

Watch how it doesn't replace all 4 Pods at once - it does a few at a time, keeping the app available throughout.

### Step 3: See the rollout history

```bash
kubectl rollout history deployment/web
```

### Step 4: Roll back to the previous version

```bash
kubectl rollout undo deployment/web
kubectl rollout status deployment/web
```

### Step 5: Confirm the image reverted

```bash
kubectl get deployment web -o jsonpath='{.spec.template.spec.containers[0].image}'
```

## Check Your Understanding

**Q1: Does a rolling update take down the whole app at once?**

<details><summary>Answer</summary>

No - by default it replaces Pods gradually (controlled by maxUnavailable/maxSurge settings), keeping some old or new Pods available throughout.

</details>

**Q2: What command reverts a Deployment to its previous version?**

<details><summary>Answer</summary>

`kubectl rollout undo deployment/<name>`.

</details>

**Q3: What happens if you push a broken image during a rolling update?**

<details><summary>Answer</summary>

The rollout stalls - Kubernetes won't finish replacing all old Pods with broken new ones, since new Pods will fail their readiness checks (or fail to even start) - this is a safety feature, not a bug.

</details>

## Common Mistakes

- **Panicking when a rollout appears stuck instead of checking why** - Use `kubectl rollout status` and `kubectl describe pod <new-pod>` to see exactly why new Pods aren't becoming ready before assuming something is broken.
- **Forgetting rollback is available and manually re-applying the old YAML instead** - `kubectl rollout undo` is simpler and uses Kubernetes' own revision history - no need to hunt down your old YAML file.

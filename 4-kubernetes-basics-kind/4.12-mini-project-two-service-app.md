# 4.12 Mini-Project: Deploy a 2-Service App with a Service Exposing It

## Concept Recap

This project combines Deployments, Services, labels/selectors, ConfigMaps, and probes from this entire module.

## Objective

Deploy a small 2-tier app end-to-end using only what you've learned in Module 4, with a checklist instead of step-by-step instructions.

## Prerequisites

- Labs 4.1-4.11 complete

## Steps

### Step 1: Your checklist

1. Create a `backend` Deployment (2 replicas) using any simple image (e.g. a small custom app like Module 1's or plain `nginx`), with a readiness probe
2. Create a ClusterIP Service exposing `backend`
3. Create a `frontend` Deployment (1 replica) that, when exec'd into, can successfully reach the `backend` Service by name (use `wget` or `curl` from inside it to prove this)
4. Inject a ConfigMap value into `frontend` as an environment variable
5. Deliberately break `backend`'s readiness probe, confirm `frontend` can no longer reach it via the Service, then fix it and confirm it recovers
6. Put both deployments in their own namespace called `mini-project`


## Try It Yourself

**Exercise 1:** Once everything works, perform a rolling update on `backend` (any image tag bump) while continuously curling it from `frontend` in a loop, to confirm zero dropped requests.

<details><summary>Hint (try first without peeking)</summary>

`while true; do kubectl exec frontend-pod -- wget -qO- http://backend; sleep 1; done` in one terminal, `kubectl set image ...` in another.

</details>

## Check Your Understanding

**Q1: Self-check: can you explain why frontend reaches backend by SERVICE name and not POD name?**

<details><summary>Answer</summary>

If not, revisit Lab 4.5/4.6 - Pod names/IPs aren't stable, Service names are the stable address.

</details>

**Q2: Self-check: what would you check first if step 3's connectivity test failed?**

<details><summary>Answer</summary>

`kubectl get endpoints backend` to rule out a label-selector mismatch (Lab 4.6), before assuming a networking problem.

</details>

## Common Mistakes

- **Skipping the deliberate-break-then-fix step** - This is the most valuable part of the exercise - actually seeing a readiness failure remove a Pod from Service traffic, then recovering, cements the concept far better than reading about it.
- **Forgetting to put both deployments in the same namespace** - If frontend and backend are in DIFFERENT namespaces, the simple `http://backend` DNS name won't resolve - you'd need the longer `backend.mini-project.svc.cluster.local` form.

## Cleanup

```bash
kubectl delete namespace mini-project
```

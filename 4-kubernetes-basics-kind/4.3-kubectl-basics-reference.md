# 4.3 kubectl Basics: A Full Reference Lab

## Concept Recap

This lab is a deliberate reference sweep through the kubectl commands you'll use constantly, so you have them all in one place.

## Objective

Practice get, describe, logs, and exec across a running Pod.

## Prerequisites

- Lab 4.2 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Create something to inspect

```bash
kubectl run ref-demo --image=nginx:1.27
```

### Step 2: get: list resources

```bash
kubectl get pods
kubectl get pods -o wide
kubectl get all
```

### Step 3: describe: full detail on one resource, including recent events

```bash
kubectl describe pod ref-demo
```

The Events section at the bottom is often the FIRST place to look when something's wrong.

### Step 4: logs: see stdout/stderr from a container

```bash
kubectl logs ref-demo
kubectl logs ref-demo --follow
```

Ctrl+C to stop following.

### Step 5: exec: run a command or get a shell inside

```bash
kubectl exec ref-demo -- ls /usr/share/nginx/html
kubectl exec -it ref-demo -- bash
```

### Step 6: delete

```bash
kubectl delete pod ref-demo
```

## Check Your Understanding

**Q1: Where do you look first when a Pod isn't behaving as expected?**

<details><summary>Answer</summary>

`kubectl describe pod <name>`, specifically the Events section at the bottom - it usually explains scheduling failures, image pull errors, etc.

</details>

**Q2: What's the difference between `kubectl logs` and `kubectl exec`?**

<details><summary>Answer</summary>

`logs` shows the container's captured stdout/stderr output; `exec` runs a NEW command inside the already-running container, similar to `docker exec` from Lab 1.2.

</details>

**Q3: What does `kubectl get pods -o wide` show that plain `kubectl get pods` doesn't?**

<details><summary>Answer</summary>

Additional columns including the Pod's IP address and which node it's running on.

</details>

## Common Mistakes

- **Only using kubectl get and never describe when debugging** - get shows current state; describe shows the HISTORY of events that led there - often essential for diagnosing failures.
- **Forgetting the -- before exec's command** - `kubectl exec podname -- command` - the `--` separates kubectl's own flags from the command being run inside the container.

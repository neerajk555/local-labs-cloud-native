# 4.4 Deployments: What They Add Over Bare Pods

## Concept Recap

A Deployment manages a ReplicaSet, which manages Pods - giving you self-healing, scaling, and rolling updates that bare Pods don't have (Lab 3.3's declarative model in action).

## Objective

Create a Deployment and directly observe self-healing by deleting a Pod it manages.

## Prerequisites

- Labs 4.2-4.3 complete

## Steps

### Step 1: Create a Deployment

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=3
```

### Step 2: See the objects it created

```bash
kubectl get deployments
kubectl get replicasets
kubectl get pods
```

Notice: 1 Deployment -> 1 ReplicaSet -> 3 Pods. The Deployment manages the ReplicaSet, which manages the Pods.

### Step 3: Delete one Pod directly and watch what happens

```bash
kubectl get pods
# copy one pod name from the output, then:
kubectl delete pod <paste-one-pod-name-here>
kubectl get pods -w
```

A replacement Pod appears within seconds - THIS is self-healing, driven by the ReplicaSet noticing actual (2) doesn't match desired (3).

## Check Your Understanding

**Q1: What three objects are involved when you create one Deployment?**

<details><summary>Answer</summary>

The Deployment itself, a ReplicaSet it creates and manages, and the Pods the ReplicaSet creates and manages.

</details>

**Q2: If you delete a Pod that's part of a Deployment's ReplicaSet, what happens?**

<details><summary>Answer</summary>

A replacement Pod is created almost immediately, since the ReplicaSet continuously reconciles actual Pod count against the desired replica count.

</details>

**Q3: Could you delete the ReplicaSet directly instead of a Pod, and expect the same self-healing?**

<details><summary>Answer</summary>

No - deleting the ReplicaSet deletes its Pods too, but the Deployment would then create a NEW ReplicaSet to replace it, which then creates new Pods - same end result via a different path.

</details>

## Common Mistakes

- **Creating bare Pods for anything long-running instead of Deployments** - Almost always use a Deployment (or another controller like StatefulSet/DaemonSet - Module 5) instead of a bare Pod, specifically to get self-healing.
- **Being surprised that a deleted Pod's NAME changes on replacement** - The replacement Pod gets a new randomly-suffixed name - this is expected and is exactly why you should never rely on a specific Pod's name/IP for anything.

## Cleanup

```bash
kubectl delete deployment web
```

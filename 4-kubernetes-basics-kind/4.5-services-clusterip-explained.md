# 4.5 Services: ClusterIP Explained Before Anything Else

## Concept Recap

A ClusterIP Service is the DEFAULT and most common Service type - it gives your Deployment's Pods a single, stable, internal-to-the-cluster address, solving the exact 'Pod IPs change' problem from Lab 3.4's glossary.

## Objective

Create a Deployment and a Service, and prove the Service's address stays stable even as Pods are replaced.

## Prerequisites

- Lab 4.4 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Create a Deployment and expose it

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=3
kubectl expose deployment web --port=80 --type=ClusterIP
```

### Step 2: See the Service's stable ClusterIP

```bash
kubectl get service web
```

### Step 3: Hit it from another Pod (Services aren't reachable from your host directly by default)

```bash
kubectl run tester --image=alpine --rm -it -- sh -c 'wget -qO- http://web'
```

You're reaching all 3 backing Pods through ONE stable address.

### Step 4: Delete a backing Pod and confirm the Service address doesn't change

```bash
kubectl get pods
# delete one of web's pods
kubectl delete pod <paste-one-pod-name>
kubectl get service web
```

Same ClusterIP as before - the Service address is stable regardless of which Pods are behind it.

## Check Your Understanding

**Q1: Why is a ClusterIP Service's address stable even as Pods are replaced?**

<details><summary>Answer</summary>

The Service is a separate, persistent object with its own stable virtual IP - it's not tied to any specific Pod's lifecycle, only to the label selector that determines which Pods currently back it.

</details>

**Q2: Can you reach a ClusterIP Service directly from your laptop's browser without extra steps?**

<details><summary>Answer</summary>

No - ClusterIP is only reachable from WITHIN the cluster by default. Lab 4.3's AWS-labs equivalent (LoadBalancer/Ingress) is needed for external access.

</details>

**Q3: What actually connects a Service to the right Pods?**

<details><summary>Answer</summary>

Label selectors - the Service watches for Pods matching specific labels, exactly as introduced in Lab 3.4's glossary.

</details>

## Common Mistakes

- **Expecting to curl a ClusterIP Service from your host machine directly** - That's expected to fail - ClusterIP is cluster-internal only. Use `kubectl run` with a temporary Pod to test from inside the cluster, as shown above.
- **Assuming a Service load-balances perfectly evenly** - It typically round-robins, but isn't a sophisticated load balancer - for advanced traffic management you'd look at a service mesh, similar to App Mesh in the AWS labs.

```bash
kubectl delete deployment web
kubectl delete service web
```

# 6.1 Why Helm Exists

## Concept Recap

By now you've written a fair amount of YAML by hand. Real apps often need 5-10+ YAML files (Deployment, Service, ConfigMap, PVC...) that mostly repeat with small variations between environments. Helm packages all of that into a reusable, parameterized 'chart.'

## Objective

Understand the copy-paste problem Helm solves before writing any chart yourself.

## Prerequisites

- Module 4 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Feel the pain manually

Imagine you need to deploy the same app to `dev`, `staging`, and `prod`, each with a different replica count and image tag. Without Helm, you'd maintain 3 near-duplicate copies of every YAML file, manually keeping them in sync as the app evolves - a common source of drift and bugs.

### Step 2: Read: What a chart is

A Helm chart is a directory of templated YAML files plus a `values.yaml` file holding the environment-specific bits (replica count, image tag, etc.). One chart + three different values files replaces three near-duplicate sets of raw YAML.

## Check Your Understanding

**Q1: What problem does Helm primarily solve?**

<details><summary>Answer</summary>

Maintaining multiple near-duplicate copies of YAML for different environments or instances of the same app.

</details>

**Q2: What are the two main pieces of a Helm chart?**

<details><summary>Answer</summary>

Templated YAML files, and a values.yaml file supplying the specific values that fill in those templates.

</details>

## Common Mistakes

- **Assuming Helm is required for all Kubernetes work** - Plenty of simple, single-environment deployments are fine with plain kubectl apply - Helm earns its complexity once you have real duplication to eliminate.

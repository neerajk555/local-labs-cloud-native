# 7.1 Why Ingress Exists (vs. Plain Services)

## Concept Recap

A ClusterIP Service (Lab 4.5) is internal-only. A separate LoadBalancer Service per app gets expensive and doesn't let you route by hostname/path. Ingress is a single entry point that can route external traffic to MANY different Services based on hostname or URL path.

## Objective

Understand the specific gap Ingress fills before installing anything.

## Prerequisites

- Lab 4.5 complete

## Steps

### Step 1: Read: The problem with one LoadBalancer per app

If you had 10 different apps in your cluster, each needing external access, giving each its own LoadBalancer Service means 10 separate external IPs/load balancers - expensive in real cloud environments (this is exactly why the AWS labs used one shared ALB pattern instead of one per lab).

### Step 2: Read: What Ingress adds

One Ingress controller (like ingress-nginx) runs as the SINGLE entry point, and Ingress RESOURCES (simple YAML rules) tell it 'requests for a.example.com go to service-a, requests for b.example.com go to service-b.' You get host- and path-based routing to many backend Services through one external address.

## Check Your Understanding

**Q1: What's the main cost/complexity problem Ingress solves compared to one LoadBalancer Service per app?**

<details><summary>Answer</summary>

It avoids needing a separate external load balancer/IP per application - one Ingress controller can route to many backend Services.

## Common Mistakes

- **Confusing an Ingress resource with the Ingress controller** - The Ingress resource is just a routing RULE (YAML); the controller (like ingress-nginx) is the actual running software that reads those rules and does the routing - you need both.

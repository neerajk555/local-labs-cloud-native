# 7.3 Host-Based Routing

## Concept Recap

Host-based routing sends traffic to different backends depending on the HOSTNAME in the request (e.g. a.example.com vs b.example.com), even though both hit the same IP/port.

## Objective

Route two different hostnames to two different backend Services through one Ingress.

## Prerequisites

- Lab 7.2 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Deploy two distinct backends

```bash
kubectl create deployment app-a --image=hashicorp/http-echo -- -text='response from app-a'
kubectl create deployment app-b --image=hashicorp/http-echo -- -text='response from app-b'
kubectl expose deployment app-a --port=5678
kubectl expose deployment app-b --port=5678
```

### Step 2: Create a host-based Ingress

```bash
cat > ingress-host.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: host-based
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: a.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-a
                port:
                  number: 5678
    - host: b.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-b
                port:
                  number: 5678
EOF
kubectl apply -f ingress-host.yaml
```

**Using VS Code instead of the heredoc above:**

1. In VS Code's Explorer panel, create a new file named `ingress-host.yaml` in your current lab folder (right-click the folder → New File, or `Ctrl+N` then save as `ingress-host.yaml`).
2. Paste this content and save (`Ctrl+S`):

Any remaining commands in this step (the ones without a `cat > ... <<EOF` block) still need to run in a terminal — use VS Code's built-in one via **Terminal → New Terminal** (or `` Ctrl+` ``) so you don't need to switch windows.

### Step 3: Test using Host headers (no need to edit /etc/hosts for this)

```bash
curl -H 'Host: a.local' http://localhost/
curl -H 'Host: b.local' http://localhost/
```

Same URL (localhost), different Host header, different response - that's host-based routing.

## Check Your Understanding

**Q1: What HTTP header does host-based routing actually inspect?**

<details><summary>Answer</summary>

The `Host` header - which is why you can test it with `curl -H 'Host: ...'` without needing real DNS or /etc/hosts entries.

</details>

**Q2: Do a.local and b.local need to be registered anywhere for this lab to work?**

<details><summary>Answer</summary>

No, not for curl testing with explicit Host headers - real browser access would need either a DNS entry or a local /etc/hosts entry mapping those names to 127.0.0.1.

</details>

## Common Mistakes

- **Trying to open a.local in a browser without an /etc/hosts entry** - Browsers don't let you set a custom Host header easily - for real browser testing (not curl), add `127.0.0.1 a.local b.local` to your /etc/hosts file first.
- **Forgetting ingressClassName: nginx** - Without specifying which Ingress controller should handle this resource, it may not be picked up at all in clusters with multiple controllers - always set it explicitly.


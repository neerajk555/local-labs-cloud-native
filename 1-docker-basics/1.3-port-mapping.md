# 1.3 Port Mapping Explained and Practiced

## Concept Recap

A container's network is isolated from your host by default. `-p hostPort:containerPort` punches a hole so traffic to a port on your machine gets forwarded into the container.

## Objective

Understand and practice mapping container ports to host ports, including common mistakes.

## Prerequisites

- Module 0 complete

## Steps

### Step 1: Run nginx WITHOUT port mapping

```bash
docker run -d --name no-port nginx
```

Try to visit http://localhost - it won't work, because nothing on your host is listening yet.

### Step 2: Run nginx WITH port mapping

```bash
docker run -d --name with-port -p 8080:80 nginx
```

Now visit http://localhost:8080 - this works, because host port 8080 is now forwarded to the container's port 80.

### Step 3: Confirm the mapping

```bash
docker port with-port
```

## Check Your Understanding

**Q1: In `-p 8080:80`, which number is the HOST port and which is the CONTAINER port?**

<details><summary>Answer</summary>

8080 is the host port (what you type in your browser); 80 is the port the app inside the container is actually listening on.

</details>

**Q2: Can two containers both map to host port 8080 at the same time?**

<details><summary>Answer</summary>

No - you'll get an error that the port is already allocated. Host ports must be unique per container.

</details>

**Q3: Can two containers both listen on container port 80 internally?**

<details><summary>Answer</summary>

Yes, easily - internal container ports don't collide with each other, only host port mappings can conflict.

</details>

## Common Mistakes

- **Forgetting -p entirely and wondering why localhost doesn't respond** - Without an explicit mapping, nothing on the host is listening - the container's network is isolated.
- **Mixing up host and container port order** - It's always `-p HOST:CONTAINER`, not the other way around.

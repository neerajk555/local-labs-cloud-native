# 1.4 Bind Mounts vs. Named Volumes (The #1 Beginner Confusion)

## Concept Recap

Container filesystem changes vanish when the container is removed (Lab 0.3). To persist data, or to share files between your host and a container, you need a MOUNT. There are two kinds: a **bind mount** maps a specific folder on your HOST machine into the container (you control the exact host path). A **named volume** is storage managed BY Docker itself - you don't need to know or care where it physically lives on disk.

## Objective

Use both a bind mount and a named volume, and understand when to use which.

## Prerequisites

- Lab 1.1 complete

## Steps

### Step 1: Create a folder on your host with a file

```bash
mkdir -p ~/bind-demo
echo 'hello from host' > ~/bind-demo/index.html
```

### Step 2: Bind-mount it into nginx

```bash
docker run -d --name bind-test -p 8082:80 -v ~/bind-demo:/usr/share/nginx/html nginx
```

Visit http://localhost:8082 - you'll see YOUR file being served.

### Step 3: Edit the host file and refresh your browser

```bash
echo 'edited from host!' > ~/bind-demo/index.html
```

No container restart needed - the change is reflected immediately.

### Step 4: Now try a named volume instead

```bash
docker volume create my-named-volume
docker run -d --name volume-test -v my-named-volume:/data alpine sleep 300
```

### Step 5: Write data into the named volume

```bash
docker exec volume-test sh -c 'echo persisted > /data/file.txt'
```

### Step 6: Remove the container, then reattach the SAME volume to a new one

```bash
docker rm -f volume-test
docker run --rm -v my-named-volume:/data alpine cat /data/file.txt
```

The data survived even though the original container is gone.

## Check Your Understanding

**Q1: Which mount type would you use to let a container read files you're actively editing on your laptop (e.g. during development)?**

<details><summary>Answer</summary>

A bind mount - it maps a specific host path you control.

</details>

**Q2: Which mount type is generally recommended for production data you don't need to browse directly on the host?**

<details><summary>Answer</summary>

A named volume - Docker manages its lifecycle and location, which is safer and more portable.

</details>

**Q3: If you remove a container, does its bind-mounted host data disappear?**

<details><summary>Answer</summary>

No - bind-mounted host files are untouched by container removal, since they live on your host filesystem independently.

</details>

**Q4: If you remove a named volume itself (not just the container) with `docker volume rm`, is the data recoverable?**

<details><summary>Answer</summary>

No - removing the volume permanently deletes its data.

</details>

## Common Mistakes

- **Confusing -v syntax order** - It's `-v host_path_or_volume_name:container_path` - same HOST:CONTAINER order as ports.
- **Forgetting a named volume persists after container removal** - This is a feature, not a bug - but it means orphaned volumes can accumulate; check with `docker volume ls`.

## Cleanup

```bash
docker rm -f bind-test 2>/dev/null || true
docker volume rm my-named-volume
rm -rf ~/bind-demo
```

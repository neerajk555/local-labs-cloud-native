# 1.5 Environment Variables and .env Basics

## Concept Recap

Environment variables let you configure a container's behavior without rebuilding the image - the same image can run differently in dev vs. production just by changing what's passed in.

## Objective

Pass environment variables to a container both individually and via a file.

## Prerequisites

- Module 0 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Pass a single variable

```bash
docker run --rm -e GREETING=hello alpine sh -c 'echo $GREETING'
```

### Step 2: Pass multiple variables

```bash
docker run --rm -e GREETING=hello -e NAME=world alpine sh -c 'echo $GREETING $NAME'
```

### Step 3: Create a .env file instead

```bash
cat > demo.env <<'EOF'
GREETING=hi
NAME=there
EOF
```

**Using VS Code instead of the heredoc above:**

1. In VS Code's Explorer panel, create a new file named `demo.env` in your current lab folder (right-click the folder → New File, or `Ctrl+N` then save as `demo.env`).
2. Paste this content and save (`Ctrl+S`):

```
GREETING=hi
NAME=there
```

Any remaining commands in this step (the ones without a `cat > ... <<EOF` block) still need to run in a terminal — use VS Code's built-in one via **Terminal → New Terminal** (or `` Ctrl+` ``) so you don't need to switch windows.

### Step 4: Use the file with --env-file

```bash
docker run --rm --env-file demo.env alpine sh -c 'echo $GREETING $NAME'
```

## Check Your Understanding

**Q1: What's the advantage of --env-file over multiple -e flags?**

<details><summary>Answer</summary>

It keeps configuration in one reviewable file instead of a long, error-prone command line, and makes it easy to swap entire configs.

</details>

**Q2: If the same image is run with different environment variables, does the image change?**

<details><summary>Answer</summary>

No - the image is identical; only the running container's behavior changes based on what it reads from the environment.

</details>

**Q3: Should you commit a .env file containing secrets to git?**

<details><summary>Answer</summary>

No - .env files often hold passwords/API keys and should be gitignored; use a secrets manager for production.

</details>

## Common Mistakes

- **Committing .env files with real secrets to version control** - Add `.env` to `.gitignore` - use `.env.example` with placeholder values instead.
- **Expecting -e values to persist after the container is removed** - They're just runtime configuration - they exist only for that container's lifetime.

# 1.10 Container Networking Deep Dive

## Concept Recap

By default, Docker creates containers on the 'default bridge' network, where containers can't resolve each other by name. A USER-DEFINED bridge network gives you automatic DNS - containers can reach each other by container name, which is essential for multi-container apps.

## Objective

Compare the default bridge network to a user-defined one, and see DNS resolution in action.

## Prerequisites

- Lab 1.1 complete
- (Optional but recommended) VS Code open on this project's folder — see `../USING-VSCODE.md` if you haven't set this up yet

## Steps

### Step 1: Try DNS on the default network (it fails)

```bash
docker run -d --name web1 nginx
docker run --rm alpine ping -c 2 web1
```

This fails - the default bridge network doesn't do automatic name resolution between containers.

### Step 2: Create a user-defined network

```bash
docker network create my-net
```

### Step 3: Run both containers on it

```bash
docker rm -f web1
docker run -d --name web1 --network my-net nginx
docker run --rm --network my-net alpine ping -c 2 web1
```

This works - user-defined networks provide automatic DNS by container name.

### Step 4: List all networks

```bash
docker network ls
```

### Step 5: Inspect your network to see connected containers

```bash
docker network inspect my-net
```

## Check Your Understanding

**Q1: Why doesn't the default bridge network support container-name DNS resolution?**

<details><summary>Answer</summary>

It's a legacy behavior kept for backward compatibility - Docker recommends user-defined networks for anything beyond trivial single-container use.

</details>

**Q2: If two containers are on DIFFERENT user-defined networks, can they reach each other by default?**

<details><summary>Answer</summary>

No - network isolation applies between separate networks unless a container is explicitly connected to both.

</details>

**Q3: What real-world problem does this solve for multi-container apps?**

<details><summary>Answer</summary>

It lets services (e.g. a web app and a database) reliably find each other by a stable name, instead of hardcoding IP addresses that can change.

</details>

## Common Mistakes

- **Relying on the default bridge network for multi-container apps** - Use a user-defined network (or Docker Compose, which creates one automatically) for reliable service discovery.
- **Assuming container IP addresses are stable** - They can change on restart - always use container/service names instead of hardcoded IPs.
